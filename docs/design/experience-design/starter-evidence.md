## A2. Question protocol (before controls)

Quantities, endpoint profile, rack information, network purpose, rail preference, redundancy and placement are **separate dimensions**. None is a project “kind”. **Unknown is not false:** unanswered means not answered, and it is never treated as “no”. Counts name their scope: a group's endpoint count and its rack information describe the **same** inventory (model's overlap rule, #8 [6718326881](https://github.com/afewell-hh/hh-aid/issues/8#issuecomment-6718326881)), never added together.

| # | Question (per endpoint group unless noted) | Unlocks: BOM lines / uncertainty removed | Who can answer | Depends on | Needed for which output | Unknown, range and mixed-inventory handling | Later edits |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Q1 | How many endpoints? | Endpoint links and ports, then every switch count | Customer request; SE | — (or derived from racks × **populated** per rack; or, as a visible assumption, racks × capacity) | **Link and port counts** and everything downstream | Blank → “Not estimated — needs endpoint count”. A range (`120-136`) gives bounded lines (`16–24`). Mixed inventory uses one endpoint group per kind. | Dependent lines go stale. A mismatch with racks × populated, or more endpoints than capacity, is shown with both answers kept. |
| Q2 | What kind of endpoint? | Default links per endpoint and link rate (as assumptions with their source) | Customer; SE; profile library | — | **Link and port counts** (or a custom profile with links and rate) | Unknown → not estimated. “Custom” covers any vendor or endpoint type. | Defaults are re-derived; supplied overrides are kept. |

Every output here is a **conditional estimate** under the named endpoint profile and the listed default assumptions (hypothetical switch profiles, uplink counts). The minimum answers make a first estimate possible; they do not make it qualified or orderable.

## A3. Two from-scratch alternatives (both in the same persistent workspace)

Both alternatives open the same workspace with the same questions, essentials and answers. Neither has a sequence or a finish step; both are **progressive** disclosure (E4). They differ only in whether optional sub-groups start expanded or collapsed. The prototype implements both behind a view switch (“Optional questions: Show all / Collapse to headings”), so a session can compare them on the same task.

| Criterion | **A. Optional groups shown** (current default; hypothesis) | **B. Optional groups collapsed to headings** |
| --- | --- | --- |
| Shape | Essentials (count, endpoint type) together at the top of the first group. *How they connect*, *Where they sit*, and *Group name and leaf switch* follow as visible sub-groups. | Same essentials at the top. Each optional sub-group is an accessible disclosure (`details`/`summary`) labelled “(optional — 2 answered · 1 open)”. |
| Speed to first output | Essentials visible together on first entry (checked at 1,400 × 1,000 and 390 × 844) | Same; less scrolling past optional questions |
| Encouraging optional detail | Optional questions and their “Affects: …” are visible without a click | One click per group; the summary shows counts but hides each question's effect |
| Interdependent inputs (E4) | Count, racks and rail visible together | Visible after opening the relevant groups; still one surface |
| Return and edit (E3) | Same surface each session | Same; “Find a detail” and “Change” links open the right sub-group automatically |
| Accessibility (E2) | No reveals | Native disclosure with a visible state; not the radio conditional-reveal pattern E2 warns about |
| Completion pressure | None | None |
| Main risk | A long section may still bury what matters on later visits (HW27) | Optional questions get missed, so fewer details are recorded and assumptions stay unnoticed |

**Recommendation: A, as a hypothesis (H).** The sponsor asked to *encourage* optional detail, and A shows each optional question with its effect at no extra cost. Revision 3.1 fixed A's first-output problem by placing the essentials together first and shortening the guidance. The evidence does **not** rule out B. B is equally progressive, and E2's warning does not apply to it. **Decide with users:** run T1–T3 with half the participants in each view (UG12). Prefer B if participants in A miss the essentials or report the section as overwhelming. Prefer A if participants in B leave optional facts from the brief unrecorded.

## A4. Starter library (discovery is separate from calculation)

Model's working contract (#8 [6718326881](https://github.com/afewell-hh/hh-aid/issues/8#issuecomment-6718326881), acknowledged by lead [6718550737](https://github.com/afewell-hh/hh-aid/issues/8#issuecomment-6718550737)) is followed here: a stable starter identity with immutable revisions; views as many-to-many discovery metadata; customisation as a separate context; copied facts as **inherited assumptions pending confirmation**, never relabelled as user-supplied; source evidence and approvals not inherited.


- **One identity.** A starter is an ID + version + a set of answers + provenance (who built it, when, and with which evidence). It is a placeholder until the from-scratch tooling can author real ones.
- **Views are derived facets.** Endpoint count, rack count, topology and network purpose are computed from the starter's own answers. A starter therefore appears once in every view, and the views can never disagree about it.
- **No separate calculation semantics.** Choosing a starter copies its answers into a new project as **assumptions** marked “from starter S2 v0”. The same planning policies used from scratch then compute everything, and the user customises in the same details panel.
- **Authoring later (S `c018fa9`):** curators build starters with the same workspace and promote a project's answers to a library entry. There is no template-only editor.
- **Deferred (S already decided placeholders now and same-tool authoring later):** curation, publishing and update mechanics. Per model's contract, a later starter revision is a separate comparison candidate and never silently replaces project answers, locks or approvals.
