# First BOM experiment — delivery brief

Owner: lead, [D06 #13](https://github.com/afewell-hh/hh-aid/issues/13). Status: proposed experiment for technical design, 2026-11-10. The sponsor endorsed the screen direction and asked for tight planning toward completion. This brief sets the next bounded work; it does not declare a production stack or qualified hardware scenario approved.

## Outcome

An SE can create a saved project, customize two server classes with several network attachments, select leaf port allocation groups, generate a traceable conditional BOM, inspect connection classes, and revise the design without losing identities or counting components twice. The next review must evaluate an executable delivery plan, not another general screen alternative.

Use the exact accepted inputs in [design-checkpoint.md](design-checkpoint.md). Do not reopen settled vocabulary, screen direction or accounting contracts without a concrete conflict. Existing artifact branches remain the evidence source; integration must preserve their acceptance scope and historical versions.

## Candidate scenario and limits

Use one coherent small scenario, derived explicitly from the accepted SU/SCX/PA fixtures: a generic accelerator server class and a general-purpose/storage class; optical and integrated assemblies; at least two network intents; leaf allocations with uplink reservations, a breakout group and one intentional unused member. Select exact population counts and a pinned source switch profile in D03. Keep one shared fixture manifest so UX, engine and verifier do not silently combine different examples.

The scenario is a conditional engineering estimate. Unknown SKUs, inclusion, media, support or placement remain visible. The switch-sizing scope must be explicit: deliver a justified result for the chosen bounded case, an identified conditional bound, or a named unresolved dependency. A port-count lower bound must not be labelled an exact supported topology. Manual switch quantities may be an explicit assumption, never the whole eventual sizing solution.

The complete experiment should contain useful server/attachment BOM lines even when some switch or media lines remain unresolved. A production-ready, orderable whole-project BOM is a later readiness level. Do not silently drop switch infrastructure, OOB dependencies or ancillary categories to make the result appear complete.

## Demonstration and acceptance examples

| Step | Observable result |
| --- | --- |
| Create and save | Two class populations; one physical server identity across every attachment. Close/reopen preserves input state and source revisions. |
| Customize | Change one dual-port DPU to two single-port DPUs; preserve two frontend links while exposing the extra adapter and management interface. No invented vendor qualification. |
| Define destination | Select fabric context, leaf deployment context and allocation group; inspect selector expansion and explicit order without needing final switch-instance bindings. |
| Generate | Per-unit quantities expand into installed/purchase lines. Bundled coverage, unresolved inclusion, separate optics and unique shared assemblies retain traceable identities. |
| Inspect | Top-level BOM expands without quantity changes. Connection-class rows expose both ends, member counts, exceptions and edit shortcuts; manual notes have a field/member/revision scope. |
| Explain failure | Two four-child parents exceed a shared budget of six despite only two selected members. Unknown unused-parent mode leaves budget unresolved. No silent relaxation. |
| Refine and regenerate | Change count or group membership; preserve prior output and commitments, mark affected lines/inspection stale, and show a meaningful diff. Identical input/evidence yields identical semantic output. |
| Refresh evidence | A controlled catalog revision change is an explicit test fixture; show affected evidence and results without mutating historical output. Do not invent a newly released Hedgehog version. |

Required acceptance evidence is executable behavior plus an independent expected-result check. The static arithmetic scripts are reference examples, not sufficient proof of an application. Export/reimport of the project and a machine-readable BOM should make the experiment reproducible; architecture proposes the minimal format. A human-readable BOM is the primary engineering output.

## Scope boundaries

In this experiment: persistent partial projects, scoped server profiles, arbitrary per-unit items, allocation groups, conditional sizing/accounting for the selected case, grouped manual connection review, trace/diff and versioned evidence. Prefer a single-user runnable setup as an experiment simplification; architecture must compare it with a shared-service path and label that choice as a proposal, not sponsor deployment policy.

Deferred: broad starter catalog population, exhaustive automated optics qualification, external fiber/structured cabling BOMs, procurement transactions, live deployment, multi-user collaboration infrastructure, full topology optimization and complete wiring export. Preserve eventual exact Hedgehog topology coverage in the coverage ledger. Where the bounded engine actually emits wiring, use the pinned upstream validator; do not fabricate wiring merely to gate an earlier BOM.
